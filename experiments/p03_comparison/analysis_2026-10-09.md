# P03·P05 결과 해석 — 데이터 편향과 score의 의미

2026-10-09, 소유자의 분석 요청. 대상은 `314a36b` 시점의 P03 비교·P05 calibration 산출물이다. 실험 해석과 후속 우선순위에 대한 분석이며 구현의 독립검증 합격 판정은 아니다. GPU 재실험·재학습·mutation testing은 수행하지 않았다.

## 판단

현재 조건에서 primary SigLIP 선택은 합리적이다. 다만 거의 완벽한 ROC-AUC가 실제 photographic realism 측정을 입증하지는 않는다. 우선 확인할 가설은 **모델이 촬영 사실성 외에 데이터 출처·압축·구도의 차이를 이용하는가**이다. 현재 분석은 그 가능성을 뒷받침하는 데이터 구성 차이를 확인했으며, 모델의 실제 의존도나 성능 부풀림의 크기를 측정한 것은 아니다.

## 직접 확인한 사실

### 1. 모델 선택

- [comparison.json](comparison.json)의 100회 원시 latency에서 median을 다시 계산했다. SigLIP 9.6331415ms, DINO 12.406617ms로 SigLIP이 22.35% 짧다. forward 시간이며 실제 서비스 응답 시간은 아니다.
- validation AUC 차이 0.000102는 [사전 선택 규칙](../../docs/plan/phase_3_baseline_comparison.md)의 0.001 미만이다. 따라서 속도로 SigLIP을 고르는 결론은 규칙과 일치한다.
- 두 실험의 `dataset_version`이 현재 metadata SHA256과 일치한다. 단일 seed·고정 224 입력의 비교이며, 반복 학습의 변동이나 모델 계열 전체의 우열은 측정하지 않았다.
- latency는 모델별 한 번의 연속 측정이다. 배포 판단이 민감해지면 측정 순서 교차·반복 및 decode/전처리 포함 지연을 별도로 측정할 수 있다.

### 2. 라벨과 겹치는 데이터 제작 조건

`data/metadata.csv` 6,000행 및 대응 이미지의 JPEG/PNG 헤더를 전수 읽었다.

| 항목 | REAL | Generated |
| --- | --- | --- |
| 표본 수 | 3,000 | 3,000 |
| 저장 형식 | JPG 3,000 | PNG 3,000 |
| 원본 가로 크기 | 800px 2,998장, 799px·900px 각 1장 | 832px 전량 |
| 원본 해상도 종류 | 25종 | 832×1216 1,500장 + 832×832 1,500장 |
| 출처 | `kfashion` 전량 | 생성기 5종, 공통 생성 파이프라인 |

[Dataset](../../src/dataset.py)은 파일을 RGB로 읽고 224×224로 변환하므로 확장자나 원본 크기가 모델 입력에 직접 전달되지는 않는다. 그러나 압축 흔적·리샘플링·구도 차이가 픽셀에 남는지는 별도 실험 대상이다. 학습 시 JPEG augmentation(p=0.5)은 존재하지만, 이것만으로 편향 제거를 입증할 수 없다.

[생성 코드](../../scripts/generate_ai.py)의 모든 prompt에는 `full-body shot`이 붙는다. 확인한 REAL 예시 `621167`·`140859`에는 상체 확대/머리 잘림이 있었고, Generated 예시 `gen_000677`·`gen_000680`은 전신 위주의 구도였다. 이 4장 관찰은 구도 편향 가설의 예시이며 전체 빈도 추정이 아니다.

Test B에서도 REAL 출처 및 GEN 저장·생성 조건은 유지된다. 따라서 unseen generator 성공만으로 이런 공통 단서를 배제할 수 없다. 유사한 JPEG·크기 편향은 [Grommelt et al., Fake or JPEG?](https://arxiv.org/abs/2403.17608)에서도 실험되었다. 이 외부 연구가 현재 모델의 편향을 직접 증명하는 것은 아니다.

### 3. 현재 score는 양 끝에 집중된다

[저장한 validation logit](../p05_calibration/validation_predictions.csv)에 [고정 temperature](../p05_calibration/calibration.json)를 적용해 다시 계산했다.

- 820장 중 **786장(95.85%)**이 score <1 또는 >99.
- 820장 중 **811장(98.90%)**이 score <10 또는 >90.
- score 10~90에 있는 표본은 **9장**이다.

이는 현재 validation에서 양 클래스가 강하게 분리된다는 뜻이다. 그 자체가 결함은 아니지만, 60/70/80점이 사람에게 구별되는 사실성 수준이라는 근거도 아니다. 학습 타깃은 REAL/Generated이고, temperature scaling도 그 라벨에 대한 확률 보정이다. 자연스러운 생성 이미지와 강하게 보정한 실촬영 사진의 체감 순위를 별도로 살펴볼 필요가 있다. 사람 평가는 현 사양 §21에서 MVP 이후 항목이므로 이번 분석으로 필수 게이트를 새로 만들지는 않는다.

[P05 metrics](../p05_calibration/metrics.json)의 Test B NLL/Brier 악화는 보고서에 이미 정확히 공개되어 있다. T<1은 확률을 양 끝으로 더 밀어낸다. 다만 악화 원인을 일부 고확신 오답·생성기 변화·REAL 비율 변화 중 하나로 단정할 수는 없으며, 표본별 loss 변화와 클래스별 지표가 필요하다. validation REAL 비율은 452/820, Test B는 448/1048이다. 현재 aggregate 수치만으로 유의한 악화라고도 판정하지 않는다.

### 4. Test B와 최종 평가의 역할

Standard test REAL 재사용 자체는 train/val 누출이 아니다. 같은 REAL을 고정하므로 생성기 변화에 따른 비교에는 유용하다. 다만 A/B는 독립된 표본 집합이 아니며 합산 표본 수나 신뢰구간 계산에서 공유 REAL을 중복 독립 표본으로 취급하면 안 된다.

현재 결과를 보며 후속 설계를 진행하므로, 최종 일반화 주장을 위한 별도 미사용 holdout을 권한다. 동일 파이프라인에서 이미지만 추가하는 것으로 위 편향이 해결되지는 않는다. 새로운 REAL 출처, 촬영/구도 범위, 생성기와 프롬프트, 양 클래스의 저장·압축 조건을 평가 목적에 맞게 설계하고 모델/threshold를 고정한 후 평가해야 한다. 기존 Test A/B는 개발 회귀 평가로 유지할 수 있다.

### 5. P06의 100개 검토 조건

P05 지표에서 calibrated threshold 기준 오분류는 A 5장(REAL 4 + GEN 1), B 11장(REAL 4 + GEN 7)이다. 공유 REAL의 동일 예측을 기준으로 고유 오분류는 **12장**에 해당한다. 표본별 ID 대조는 P06 추출 시 확인해야 한다.

따라서 현재 오분류만으로 §27의 최소 100개 검토 조건을 채울 수 없다. 모든 오분류를 먼저 검토하고 low-confidence·변환에 민감한 사례·모델 간 불일치·고확신 사례를 더해 검토군을 구성하는 방안을 권한다. 보충 사례를 오분류라고 기록하면 안 되며, 이것을 완료 조건에 어떻게 반영할지는 P06 계획에서 명시해야 한다. 이번 분석은 그 조건을 변경하지 않는다.

## 권장 후속 순서

1. 고정 checkpoint/threshold로 압축·크기·구도 통제 진단. 양 클래스에 같은 변환을 적용한 뒤 generator/source별 AUC와 원본 대비 score 변화·판정 전환을 측정한다. 변환 성능 하락만으로 편향 원인을 확정하지 않고 정보 손실의 영향도 구분한다. PNG 재저장만으로 기존 JPEG 흔적이 사라지지는 않는다.
2. GEN pHash 및 필요 시 embedding 근사중복 점검, P06 오분류·스트레스 사례 검토. 현재 split을 즉시 바꾸지 말고 발견된 중복과 영향을 먼저 기록한다.
3. 원인 분석을 바탕으로 데이터 보강·미사용 최종 holdout 설계. 현재 SigLIP baseline을 유지하고, LoRA 필요성은 통제 평가에서 나타난 실패를 근거로 재검토한다.

## 재계산 방법

아래 명령은 repo 루트에서 CPU dev 이미지의 Pillow로 이미지 헤더·score 분포·latency를 재계산한다. 이미지 디코딩 전체나 GPU 추론은 필요하지 않다. host Python stdlib의 JPEG SOF/PNG IHDR 집계에 이어 아래 명령도 실제 실행하여 수치를 확인했다. 최초 요약에서 누락한 REAL 가로 크기 예외 2장을 재현 검사에서 반영했다.

```bash
DATA_DIR="$HOME/data/tracepector/images" docker compose run --rm -T dev python - <<'PY'
import csv, hashlib, json, math, statistics
from collections import Counter
from pathlib import Path
from PIL import Image

rows = list(csv.DictReader(open('data/metadata.csv')))
digest = hashlib.sha256(Path('data/metadata.csv').read_bytes()).hexdigest()
for label in ('1', '0'):
    selected = [r for r in rows if r['label'] == label]
    sizes = Counter()
    for r in selected:
        with Image.open(Path('/data') / Path(r['path']).relative_to('images')) as im:
            sizes[im.size] += 1
    print(label, len(selected), Counter(Path(r['path']).suffix for r in selected))
    print('widths', Counter({w: sum(n for (x, h), n in sizes.items() if x == w)
                             for w, h in sizes}))
    print('dimensions', sizes)
for path in ('experiments/p02_siglip_baseline/experiment.json',
             'experiments/p03_dino_baseline/experiment.json'):
    assert json.load(open(path))['dataset_version'] == digest
comparison = json.load(open('experiments/p03_comparison/comparison.json'))
for model in comparison['models']:
    print(model['encoder'], statistics.median(model['latency_samples_ms']))
t = json.load(open('experiments/p05_calibration/calibration.json'))['temperature']
probabilities = [1 / (1 + math.exp(-float(r['logit']) / t)) for r in csv.DictReader(
    open('experiments/p05_calibration/validation_predictions.csv'))]
for low, high in ((.01, .99), (.1, .9)):
    print('tails', low, high, sum(p < low or p > high for p in probabilities))
PY
```
