# DB-08 — API 응답 분류 체계·confidence·데모 형태

**Status:** Open
**Related phase:** P07 ([계획](../plan/phase_7_api_demo.md))

## 결정이 필요한 이유

`docs/project.md` §22의 API 예시와 지금 채택된 보정 artifact가 서로 맞지 않는다. 어느 쪽을 따를지 정해야 P07-01 응답 schema를 확정할 수 있다.

- §22 예시는 `confidence` 필드를 포함하지만 의미를 정의하지 않는다.
- §22는 "Threshold는 config에서 관리"하며 `synthetic_like: 40`, `uncertain: 70`의 3단계 예시를 든다.
- 반면 P05에서 정해 P09까지 이어진 보정 계약은 validation에서 고른 **확률 threshold 1개**를 calibration artifact가 소유하는 2단계 분류다. 현재 값은 0.2351, 점수로 23.5다. SoT(`docs/sot.md`)도 threshold 소유자를 calibration artifact로 적고 있다.
- 예시대로 40/70을 쓰면 23.5~40 구간 이미지의 분류가 현재 보정 결과와 달라진다.

데모 형태는 사양에 `demo/app.py`라는 이름만 있고 정해진 것이 없다. 새 의존성과 실행 구조가 달라지므로 함께 묻는다.

## 결정 1 — 분류 체계와 threshold 소유

| 옵션 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 지금의 2단계 유지. threshold는 calibration artifact가 소유하고(현재 23.5점), config는 artifact 경로만 가리킨다. §22 예시를 실제 계약으로 고친다 | 검증된 보정 결과와 일치. 값이 한 곳에만 있다. 추가 실험 없음 | §22의 "uncertain" 개념이 사라진다 |
| B | 3단계(`synthetic_like`/`uncertain`/`photographic_like`) 도입. 경계 두 개를 validation에서 사전 규칙으로 새로 정해 artifact에 넣는다 | 애매한 이미지를 따로 알려 줄 수 있다 | 경계 선정 규칙의 사전등록·재보정·검증이 추가로 필요해 P07이 늦어진다 |
| C | §22 예시대로 config에 40/70 고정값을 둔다 | 사양 문구와 같다 | 근거 없는 숫자이고 현재 보정 threshold와 충돌한다. threshold 소유자가 둘이 된다 |

## 결정 2 — `confidence` 필드

| 옵션 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 응답에서 뺀다. `realism_score` 자체가 보정된 확률(×100)이다 | 중복 없는 응답. 의미 오해 여지가 없다 | §22 예시와 필드가 달라진다 |
| B | 예측한 쪽의 보정 확률 `max(p, 1-p)`로 정의해 넣는다 | 사양의 필드를 유지한다. 계산이 단순하다 | 점수에서 바로 유도되는 중복 값이다. 기준선이 23.5라서 "photographic_like인데 confidence 0.6"처럼 직관과 어긋나는 값이 나온다 |

## 결정 3 — 데모 형태

| 옵션 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | API 서버가 정적 HTML 데모 페이지 1개를 함께 제공한다. 페이지는 같은 서버의 `POST /score`를 호출한다 | 새 의존성 없음, 컨테이너 1개. 데모가 실제 API 계약을 그대로 쓴다 | 화면을 직접 HTML/JS로 만든다 |
| B | Gradio 앱(`demo/app.py`)이 API를 호출한다 | 업로드·미리보기 UI가 기본 제공된다 | 큰 의존성 추가, 컨테이너·포트 2개 |
| C | Streamlit 앱이 API를 호출한다 | 화면 구성이 빠르다 | B와 같은 단점, 페이지 전체가 다시 실행되는 구조 |

## 권장과 이유

- **결정 1은 A**를 권한다. 독립검증까지 마친 보정 결과를 그대로 쓰고, threshold 소유자를 하나로 유지한다. "uncertain"이 꼭 필요하면 데모 문구로 점수 구간을 설명하거나, 이후 B를 별도 슬라이스로 추가할 수 있다.
- **결정 2는 A**를 권한다. 점수가 이미 보정 확률이라 `confidence`는 같은 정보를 다른 이름으로 한 번 더 보내는 셈이다. 데이터 계약 지침의 중복 필드 금지와도 맞는다.
- **결정 3은 A**를 권한다. MVP 데모 요구(업로드·미리보기·점수 표시)가 작고, API 계약을 그대로 쓰는 편이 검증하기 쉽다.

어느 쪽을 고르든 `project.md` §22 예시와 README를 결정에 맞게 고친다.
