# DB-05 — P06 100개 검토군 구성·검토 주체

**Status:** Resolved
**Related phase:** P06 ([계획](../plan/phase_6_failure_analysis.md))

## Decision needed

§27 Phase 6은 "Failure case를 최소 100개 이상 수동 검토"를 요구한다. 그러나 P05 지표 기준 calibrated threshold 오분류는 Test A 5장·Test B 11장이며, 공유 REAL을 한 번만 세면 고유 약 12장이다(표본 ID 확인은 P06-01). validation을 더해도 수 장 수준이다. 실제 오류만으로는 100개를 채울 수 없으므로 (1) 무엇을 검토군에 넣고 완료로 인정할지, (2) 수동 검토를 누가 할지 결정이 필요하다.

### 결정 1 — 검토군 구성

| Option | Description | Pros | Cons |
| --- | --- | --- | --- |
| A | 실제 오류 전수 + 보충 사례로 ≥100. 보충은 low_confidence, P06-02 통제 조건에서 판정이 전환된 사례, generator·category·종횡비 층화 고확신 사례 순. 사례마다 유형(오류/경계/스트레스/고확신)을 기록하고 "실제 오류 n개"를 별도 보고 | §27 수치 충족, 편향 가설을 사례로 확인 가능, 다음 데이터 방향에 쓸 정보가 많음 | 보충 사례는 오류가 아니므로 "failure 100개"의 문자적 의미와 다름 — 보고 시 구분 필수 |
| B | 실제 오류만 전수 검토(약 12 + val). §27의 100개 조건은 데이터·holdout 확장 후로 이월하고 project.md를 갱신 | 사양 문구의 의미(failure)를 엄격히 유지, 작업량 최소 | 패턴 일반화 근거가 매우 약함, project.md 변경 필요 |
| C | 통제 조건(P06-02)에서 판정이 틀린 사례도 "failure"로 인정해 오류만으로 100을 채움 | 검토 대상이 모두 실제 오판 | 판정 전환 수가 100에 못 미칠 수 있음(미측정), 변환된 입력의 오류는 원본 분포의 오류와 성격이 다름 |

### 결정 2 — 검토 주체

| Option | Description | Pros | Cons |
| --- | --- | --- | --- |
| R1 | 작업자(에이전트)가 이미지를 직접 보고 구조화 양식으로 1차 검토, 소유자가 일부(예: 오류 전수 + 무작위 20건) 확인 | 진행 속도, 기록 일관성 | 에이전트의 시각 판단은 사람 체감과 다를 수 있음 |
| R2 | 작업자가 검토군·양식·이미지 시트를 준비하고 소유자가 전수 검토 | 사람의 판단으로 기록 | 소유자 시간 소요, 진행이 소유자 일정에 묶임 |

## Recommendation + reason

**결정 1: A**, **결정 2: R1**. 고유 오류가 약 12장인 상황에서 B는 패턴을 말하기에 표본이 너무 적고, C는 100건 도달 여부가 불확실하다. A는 오류와 보충 사례를 구분 기록하면 사양의 의도(다음 데이터 수집 방향 결정)를 가장 잘 충족한다. 검토는 R1로 진행하되 오류 전수는 소유자 확인을 받아 에이전트 판단의 편향을 줄인다.

## Follow-up considerations

- A 선택 시 P06 완료 근거에 "검토 n건 중 실제 오류 m건"을 명시하고, project.md §27 문구 변경 없이 계획서에 해석을 기록한다.
- 보충 사례의 층화 비율과 고확신 사례 표본 수는 P06-03 착수 시 config에 고정하고 결과를 본 뒤 바꾸지 않는다.

## Deferred / out of scope

- 사람 pairwise 평가(§21), 최종 holdout 구축, 데이터 보강.
